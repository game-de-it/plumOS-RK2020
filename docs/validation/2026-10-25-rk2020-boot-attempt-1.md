# RK2020 physical boot attempt 1: stock SquashFS compression mismatch

Date: 2026-10-25

Failure evidence: `/Users/kroot/Downloads/IMG_4806.jpg`

Corrected source ref: `6da37b5`

## Observed failure

The RK2020 loaded the stock kernel and initramfs, displayed the plumOS splash,
then entered the stock initramfs debugging shell at `mount_sysroot`:

```text
*** Starting debugging shell for boot step: mount_sysroot...
*** Error in mount_sysroot: mount_common: Could not mount /flash/SYSTEM ***
```

This establishes that the Rockchip prefix, U-Boot path, KERNEL, active DTB,
panel, framebuffer, boot FAT, and `/flash` handoff were operational. The first
failure was mounting the plumOS dispatcher `SYSTEM`.

## SD readback and cause

The inserted test card was identified as `/dev/disk5`, a 62.5 GB removable
Secure Digital device with `PLUMOS_BOOT` on `/dev/disk5s1`. The card's
`SYSTEM` was present, readable, and byte-for-byte identical to the generated
artifact:

```text
SHA-256 8220be4af98a3145c78041332a737dfe05074d923f1d2199a6e08eda20fbe18e
size    823296 bytes
format  SquashFS 4.0, xz compressed
```

The failure was therefore not a truncated write or missing file. The captured
stock boot path uses gzip/zlib SquashFS support, while the first plumOS build
created the dispatcher and both A/B slots with `-comp xz`. The stock 4.4.189
kernel rejected that compression before the plumOS dispatcher could run.

## Correction

`scripts/build-system-rootfs.sh` now creates all three SquashFS artifacts with
`-comp gzip`. Both System verification paths require an exact
`Compression gzip` result, and the source gate rejects a return to `-comp xz`.

The corrected build completed:

- 12/12 source gates;
- full app-layer and license audit;
- implementation audit with 0 release blockers;
- dispatcher and System A/B extraction;
- SD filesystem readback and first-boot USER simulation;
- strict release gate for version `0.1.0-dev`.

Corrected artifacts:

| --- | ---: | --- |
| dispatcher `SYSTEM` | 999,424 bytes | `244fad153932d4991679d96906b366ab8502ea843086b05465449367ad786021` |
| System A/B squashfs | 73,908,224 bytes each | `089d37a5d4d26a25fc2625974fada9f08bed7918fd5c66b591b125f56b2ff988` |
| full SD image | 2,701,131,776 bytes | `4e244a0d90d8603d6aa1d929758b7e4c6b615657a4b238d16cef72844f17c70f` |

## Test-card update

The card was not repartitioned or reflashed. Only the dispatcher, A/B slot
files, their checksums/manifests, and the boot image metadata on
`PLUMOS_BOOT` were replaced. The app-layer partition and any ROM/USER data
were not changed.

Post-write readback verified every entry in `checksums.sha256`. macOS `file`
identified the dispatcher and both A/B slots as SquashFS 4.0 `zlib compressed`,
and both manifests record `source_ref=6da37b5`.

## Corrected-card physical result

The corrected card subsequently passed `mount_sysroot`, displayed the normal
stock startup countdown over the plumOS splash, and reached the plumOS
frontend. The user confirmed that the frontend cursor can be moved. This is
the physical acceptance result for the gzip SquashFS correction and the first
frontend/input path; it does not establish the remaining subsystem gates.

The same run exposed two follow-up items:

- the top-level Pyxel, Favorites, and Recent artwork has visibly inconsistent
  sizing on the 480x320 panel;
- the attached USB Wi-Fi dongle is reported as missing, so the V90S-derived
  `0bda:1a2b` driver-disk mode switch and RK2020 USB-host path still require
  device-log diagnosis and a physical retry.

Audio, the complete control map, Wi-Fi association/DHCP, emulator routes,
persistence, and the power lifecycle remain separate acceptance tests.
